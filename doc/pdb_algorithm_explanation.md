# Additive Pattern Database（PDB）アルゴリズム解説

## 概要

15パズルの深い解（40〜50手）を確実に解くために必要な、**Additive Pattern Database（PDB） + IDA\*** という手法の仕組みを説明します。

現在のソルバーが `2,4,0,8,9,10,12,3,6,13,7,14,5,11,15,1` という深い盤面で 180秒かけても解けない理由と、なぜ PDB があれば数秒で解けるのかを理解するための資料です。

---

## 1. なぜ普通の方法では解けないのか

### 状態爆発の原因

15パズルの全状態数は `16! ≈ 20兆`。これを全部事前計算するのは不可能です。

一方、現在実装している Manhattan 距離や Walking Distance（WD）のヒューリスティックは：
- 各タイルがゴールまで何マスか、を**独立に足すだけ**
- 実際の手数よりかなり**甘い（甘すぎる）下限値**

h値が甘いと、A\* や IDA\* は「まだ解に向かっているかもしれない」と判断する枝が大量に残り、**状態爆発**が起きます。実際に前回の測定では：

| アルゴリズム | 180秒での探索状態数 |
|---|---|
| A\*           | 214,000 |
| IDA\*         | 298,000 |
| WD+A\*        | 150,000 |
| WD+IDA\*      | 176,000 |

深い盤面（最適手数 40+ 手）では、この 150,000〜298,000 状態では足りず、タイムアウトします。

### 必要なのは「密な下限値」

PDB の発想は逆転しています：

> 全部は無理でも、**タイルを数個のグループに分けて、そのグループだけなら完全に解き切れる**

---

## 2. ① タイルをグループ分けして「抽象化」する

### 5-5-5 分割の例

15枚のタイルを3つのグループに分けます：
- **グループ1**：タイル 1〜5
- **グループ2**：タイル 6〜10
- **グループ3**：タイル 11〜15

各グループの「パターンデータベース」を作るときは、**そのグループ以外のタイルを「区別のつかない空白」とみなして無視**します。

左側のゴール盤面に3色でグループを塗り分け、右側は「グループ1 だけを残した抽象盤面」。グループ1 以外のタイル（6〜15）と空白は全て灰色で表示されます。

### 状態数の削減

グループ 1 つ分の抽象盤面：
- 5タイル＋空白＝6要素を16マスに配置
- 状態数 ≈ **570万通り**（16 × 15 × 14 × 13 × 12 × 11）

この程度なら、BFS で全パターンを走査して「最短手数表」を作ることができます。

---

## 3. ② ゴールから逆向きBFSで「最短手数表」を作る

### Retrograde BFS（逆向き幅優先探索）

各グループの抽象盤面について、**ゴール状態から逆向きに幅優先探索（BFS）**を実行します。

BFS は距離 0 から順に広がるので、ある配置に**最初に到達したとき**の距離が、そのまま「ゴールまでの最短手数」になります。これを全パターン分、`bytearray` の表に保存します。

- **グループ1の表**：PDB_G1[配置] = その配置からゴールまでの最短手数
- **グループ2の表**：PDB_G2[配置] = その配置からゴールまでの最短手数
- **グループ3の表**：PDB_G3[配置] = その配置からゴールまでの最短手数

### 🔥 このアルゴリズム最大の肝：Additive な数え方

表を作るとき、移動コストの数え方を工夫します：

```
そのグループのタイルが動いた手  → +1
空白だけが動いた手              → +0
```

**なぜ空白だけの移動を 0 にするのか？**

3つのグループの表の値を**足し算（additive）して使いたい**からです。

もし各表が「自分のグループのタイルが動いた手数」だけをカウントしていれば：
- 実際の盤面で起こる **1 手は必ずどれか 1 つのタイル**を動かす
- そのタイルはどれか 1 つのグループに属する
- つまり、3つの表が**同じ手を二重カウントすることが絶対にない**

だから安心して足し合わせられて、かつ**実際の手数を超えない（admissible）下限値**になります。

---

## 4. ③ 本番では3つの表を引いて足すだけ

### ファイル構成

PDB の構築はローカルで一度きり：

```
build_pdb.py  ← ローカルで実行（一度だけ）
  ↓
pdb_g1.bin （グループ1の表、約 1.5 MB）
pdb_g2.bin （グループ2の表、約 1.5 MB）
pdb_g3.bin （グループ3の表、約 1.5 MB）
  ↓
リポジトリにコミット
```

### 本番の探索時

API サーバーは起動時に 3 ファイルをロードしておき、探索中の**各状態について**：

```python
h = PDB_G1[state → G1の配置] + PDB_G2[state → G2の配置] + PDB_G3[state → G3の配置]
```

例えば、ある盤面に対して：
- PDB_G1 の表引き → 14
- PDB_G2 の表引き → 11
- PDB_G3 の表引き → 9
- **合計 h = 34** （下限値）

この 34 という値は、Manhattan の甘い 30 よりずっと真の手数に近いため、IDA\* は無駄な枝を一気に切り落とせます。

---

## 5. なぜ A\* ではなく IDA\* か

### メモリの問題

深い解（40〜50手）では：

| アルゴリズム | メモリ消費 |
|---|---|
| **A\*** | すべてのノード（open/closed）をメモリに保持 → **深いほど爆発** |
| **IDA\*** | 反復深化＋深さ優先 → メモリ = O(深さ) |

Render の無料枠は 512MB。A\* だとメモリが先に枯渇します。

### IDA\* + PDB の組み合わせ

Korf が 1985年にランダムな 15パズルを最適に解いた方法が、この **IDA\* + PDB** の組み合わせでした。実装するなら：

```python
h = max(h_pdb, h_walking_distance, h_manhattan_plus_lc)
```

すべて admissible（実際の手数を超えない）なので、最大値を取っても安全。一番タイトな値を選べて損がありません。

---

## 6. まとめ

このアルゴリズムの本質：

| ステップ | 内容 |
|---|---|
| **抽象化** | タイルを 3 グループに分ける |
| **事前計算** | 各グループについてゴールから逆向きBFS → 表に保存 |
| **Additive** | 空白の移動は 0 で数えて、3つの表が足し合わせられるように設計 |
| **本番** | 各状態で 3 つの表を引いて足す → h値を得る |
| **探索** | IDA\* + タイトなh値で深い解でも高速に探索 |

## 実装への道

### Phase 1: build_pdb.py（ローカル、一度だけ実行）
- 5-5-5 分割の状態ごとに retrograde BFS
- 各グループの表をバイナリファイルに保存
- 実装量：中程度

### Phase 2: solver.py に PDB ヒューリスティック追加
- 起動時に 3 ファイルをロード（BFS は走らせない）
- `h_pdb(state)` 関数を追加
- `solve_pdbidastar(board)` を新規追加
- 既存の h を `h = max(h_pdb, h_wd, h_manhattan_lc)` に変更
- 実装量：小

### Phase 3: API にパリティチェック追加
- 解けない盤面を `HTTP 400` で即座に返す
- 無駄なタイムアウトを防止
- 実装量：小

### Phase 4: ビジュアライザーに PDB+IDA\* を追加
- 5本目のアルゴリズムとして比較表に表示
- 他の 4 つとの探索状態数・実行時間を一目で比較可能に
- 実装量：小

---

## 期待される効果

例の盤面 `2,4,0,8,9,10,12,3,6,13,7,14,5,11,15,1`：

| 現在（WD+IDA\*） | PDB+IDA\* |
|---|---|
| 180秒でタイムアウト | **数秒で解ける** |
| 176,000 状態 | **5,000以下** |

h値がさらに密になれば、探索ノード数は 1/30 に削減される見込みです。
